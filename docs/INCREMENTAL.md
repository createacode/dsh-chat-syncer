# 增量同步设计调研

## 结论

当前插件提供两种用户可见的同步方式：

- **覆盖**：公共最新快照只包含本次选中的会话。
- **增量**：先读取仓库当前的公共快照，保留其中的其他会话，再合并本次选中的会话；拉取时只补缺失或远端更新的文件。

增量模式解决的是**会话集合层面的合并**，不是网络层面的最小传输。当前仓库仍以“一个快照包”为单位提交，所以增量推送会下载上一版包、解密、合并，再上传一个新的完整包。这样兼容现有加密包、HEAD 指针和回滚逻辑，但大仓库的增量推送仍会传输整包。

## 候选方案

### 1. 整包替换（覆盖模式）

- 优点：实现简单；一个 HEAD 指针原子切换；加密和校验逻辑集中。
- 缺点：每次推送都上传完整包；多设备只保留最后一次快照。
- 适用：会话数量少、单包较小、以“最新状态”为主的场景。当前默认模式即此方案。

### 2. 内容寻址对象库（推荐的真正增量）

把公共快照拆成“清单 + 会话对象”：

```text
users/<user>/common/
  HEAD.json                 # 只指向当前 manifest，最后写入
  manifest.json             # 会话列表、hash、大小、mtime
  objects/<sha256>.dsync    # 每个会话一个对象（或 .enc）
```

推送：

1. 读取远端 `manifest.json` 和本地会话哈希；
2. 只上传本地新增/变化的 `objects/<hash>`；
3. 写新 `manifest.json`；
4. 最后写 `HEAD.json`，完成原子切换；
5. 旧对象延迟清理（保留最近 N 版，避免正在拉取的设备拿到半套数据）。

拉取：

1. 读 `HEAD.json` 与 `manifest.json`；
2. 只下载本机缺失或 hash 不同的对象；
3. 校验对象 hash 后原子替换本地文件；
4. 已存在且 hash 相同的对象直接复用。

优点：

- 真正只传变化会话；
- 内容寻址天然去重；
- 中断后重试成本低；
- 旧版本可以作为恢复点保留。

需要处理：

- **原子性**：HEAD 必须最后写；对象先写、清单后写、HEAD 最后写。
- **并发**：两个设备同时推送时用 HEAD revision 比较；冲突时要求先检查或强制覆盖。
- **加密**：对象单独 AES-256-GCM 加密；对象名用明文内容 hash（不泄露会话名），或使用随机对象 id + 加密清单隐藏 hash。
- **垃圾回收**：删除无引用对象前保留宽限期；至少保留上一版，避免拉取中的设备缺对象。
- **清单大小**：会话很多时清单会变大，可按用户/工作区分片。
- **Git 平台限制**：Gitee/GitHub contents API 逐文件提交；对象多时请求数增加，需要批量/重试和限流。

### 3. Git 自身的增量对象

如果直接使用 Git 客户端，Git 的 packfile 只传输变化 blob，天然增量。但插件刻意不依赖本机 Git，也不要求用户配置 SSH/凭据；同时 Git 历史会包含会话内容，删除和加密策略更复杂。因此暂不采用。

### 4. 二进制 delta / rsync

对单个大包做二进制差分，只上传 patch。优点是传输小；缺点是需要稳定的基线、patch 链管理和冲突处理，且加密包的随机 IV 会让字节级 diff 失效，不适合作为第一版。

## 选择

当前版本选择**语义增量 + 整包提交**：

- 不改变现有仓库结构和加密格式；
- 旧版本插件仍能读取；
- 能够满足“保留远端其他会话、只合并选中会话”的需求；
- 大包传输问题留到对象库方案解决。

后续若升级到内容寻址对象库，应保持 `HEAD.json.revision` 的 `SYNC-...` 命名规则不变；对象库只是 HEAD 指向的存储后端，设备比较逻辑不变。

## 同步值命名

推荐格式：

```text
SYNC-<UTC yyyyMMddHHmmss>-<6 位随机数字>
例：SYNC-20261109145500-042317
```

- 前缀是英文 `SYNC`；
- 后面全部是数字；
- 时间戳保证大致按时间排序；
- 6 位随机数降低同一秒并发碰撞；
- 不包含设备名、账号、仓库名或会话内容；
- 包完整性另用 `dataSha256`，不把哈希当同步值。
